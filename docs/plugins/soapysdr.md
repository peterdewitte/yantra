# Plugin: soapysdr (SDR receiver, SoapySDR)

`soapysdr.so` (plugin id `soapysdr`, RAD-62): any radio of the
SoapySDR modules built in, except the HackRF (which has its own plugin):
the RTL-SDR (osmocom librtlsdr, also the RTL-SDR Blog V4), the Airspy and
network radios through SoapyRemote. How the layer works:
[RADIO_PLUGINS.md, the SoapySDR plugins](../RADIO_PLUGINS.md#the-soapysdr-plugins-rad-54-rad-62).
Capabilities HOTPLUG, SCAN and SPECTRUM (an averaged FFT of its own
samples, radio API 1.2, RAD-140). Hardware results:
[DEVICES.md](../DEVICES.md).

## Devices

Key `<driver>:<serial>` (`rtlsdr:...`, `airspy:...`,
`remote:...`). Network radios are the SoapySDRServers named in
`YANTRA_SOAPY_REMOTE` (`host[:port]`, comma-separated); there is no
network discovery. Without a device the diagnostic lists the modules and
versions and the usual reasons (not plugged in, udev rules, the DVB-T
driver of an RTL-SDR: `udev/yantra-rtl-sdr-blacklist.conf`).

## Records

`tetra_cell`, `tetra_neighbour` and `tetra_scan` in dBFS (no
SELF_CALIBRATED, no C1: Yantra calibrates per gain combination). Fields:
[TETRA_RECORDS.md](../TETRA_RECORDS.md).

## Known issues

- None of the radios is measured on real hardware yet (DEVICES.md).
- PlutoSDR, bladeRF, LimeSDR and USRP are not built in (THIRD_PARTY.md:
  licence or library questions for the owner).
- An RTL-SDR needs the DVB-T kernel driver blacklisted (or it is busy).
